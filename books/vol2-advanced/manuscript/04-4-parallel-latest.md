# 4-4. 병렬 작업 — Worktree·Agent View·/goal·Dynamic workflows

> 학습 목표: 2026-05 신기능으로 충돌 없이 여러 작업을 동시에 굴린다.
> 선수 지식: 4-1(서브에이전트 오케스트레이션). · 원천: manifest #53~#58
> 이 장은 이 책의 **최신성**을 가장 잘 보여 주는 장이다.

한 세션으로 한 가지 일을 하는 단계는 지났다. 진짜 생산성은 **동시에 여러 일을
굴릴 때** 나온다. 문제는 충돌이다. 두 작업이 같은 파일을 동시에 고치면 서로의
결과를 덮어쓴다. 2026-05에 정식화·도입된 도구들이 바로 이 문제를 푼다.

네 가지를 차례로 본다. 각각 푸는 문제가 다르다.

## Worktree — 충돌 없이 갈라서 일하기

**푸는 문제**: 같은 저장소에서 두 가지 작업을 동시에 하면 파일이 엉킨다.

Worktree는 같은 Git 저장소를 **물리적으로 분리된 작업 폴더**로 복제한다. 작업
A는 A의 워크트리에서, 작업 B는 B의 워크트리에서 돈다. 서로의 파일을 건드리지
않으니 충돌이 원천 차단된다. 끝나면 각자의 브랜치로 합치면 된다.

언제 쓰나. 한 기능을 짜면서 동시에 급한 버그를 고쳐야 할 때. 같은 마이그레이션을
두 가지 방식으로 시도해 보고 더 나은 쪽을 고를 때. 작업이 끝나고 워크트리에
변경이 없으면 자동으로 정리된다.

> **함정** — 워크트리는 디스크와 설정 비용이 든다. "혹시 몰라서" 남발하지
> 말자. 같은 파일을 동시에 고치는 병렬 작업일 때만 쓴다. 그 외에는 그냥
> 브랜치만 갈라도 충분하다.

## Agent View — 여러 세션을 한 화면에서

**푸는 문제**: 세션을 여러 개 띄우면 어디서 뭐가 도는지 놓친다.

Agent View는 동시에 도는 여러 세션을 **한 화면에서** 관리한다. 어느 세션이
일하는 중이고, 어느 세션이 내 승인을 기다리는지 한눈에 보인다. 병렬 작업이
서너 개로 늘어나는 순간부터 없으면 안 되는 도구다.

워크트리가 '작업을 물리적으로 가른다'면, Agent View는 '가른 작업들을 한눈에
본다'. 둘은 짝으로 쓴다.

## /goal — 조건이 충족될 때까지 자율로

**푸는 문제**: "될 때까지 해 줘"를 매번 지켜보고 다시 시켜야 한다.

`/goal`은 **목표(조건)를 걸어 두면, 그게 충족될 때까지 스스로 진행**한다.
중간에 멈추려 해도, 조건이 아직 안 됐으면 다시 일을 잡는다. 예를 들어 "CI가
초록불이 될 때까지"를 목표로 걸면, 실패할 때마다 원인을 진단하고 고치고 다시
돌리기를 반복한다. 사람이 매번 "다시 해"라고 칠 필요가 없다.

쓰는 법은 단순하다. 목표를 한 문장으로 적어 `/goal`로 건다. 조건이 충족되면
자동으로 풀린다.

> **함정** — 목표를 모호하게 걸면 영원히 안 끝난다. "좋게 만들어 줘"가 아니라
> "테스트 전부 통과 + 린트 0건"처럼 **판정 가능한 조건**으로 걸어야 한다.

## Dynamic workflows — 스크립트로 굴리는 대규모 오케스트레이션

**푸는 문제**: 수십 개 작업을 일정한 구조로, 사람 개입 없이 병렬 처리해야 한다.

지금까지의 세 도구가 '사람이 모는 병렬'이라면, Dynamic workflows는 **스크립트가
모는 병렬**이다. 작업을 어떻게 나누고(fan-out), 어떻게 검증하고, 어떻게
합칠지를 코드로 적어 둔다. 그러면 수십 개의 서브에이전트가 그 구조대로
동시에 일한다. 큰 마이그레이션, 코드베이스 전수 감사, 광범위한 일괄 변경처럼
한 세션의 머리로는 다 들고 있을 수 없는 규모를 다룰 때 쓴다.

핵심 패턴은 셋이다.
- **fan-out**: 일을 잘게 나눠 동시에 처리.
- **verify**: 결과를 독립적으로(때로는 적대적으로) 검증.
- **synthesize**: 검증된 결과를 하나로 합침.

4-1의 서브에이전트 오케스트레이션이 '모델이 판단하며 모는' 방식이라면, 이쪽은
'스크립트가 결정론적으로 모는' 방식이다. 흐름을 사람이 못 박고 싶을 때 이걸
쓴다.

## 무엇을 언제 쓰나 — 한 장 비교표

| 도구 | 푸는 문제 | 누가 모나 | 언제 |
|------|-----------|-----------|------|
| Worktree | 파일 충돌 | 사람 | 같은 저장소, 동시 작업 |
| Agent View | 세션 가시성 | 사람 | 병렬 세션이 3개 이상 |
| `/goal` | 반복 재지시 | 자율(조건) | "될 때까지" 류 작업 |
| Dynamic workflows | 대규모 병렬 | 스크립트 | 수십 개 작업, 구조 고정 |

이 넷은 경쟁이 아니라 **층위**다. 워크트리로 가르고, Agent View로 보고,
`/goal`로 자율 진행시키고, 규모가 커지면 Dynamic workflows로 코드화한다.

## 실습 — 워크트리 2개 병렬 + /goal

1. 기능 작업용 워크트리와 버그 수정용 워크트리를 따로 연다.
2. 각 워크트리에서 세션을 띄우고 Agent View로 둘을 함께 본다.
3. 버그 수정 세션에 "테스트 전부 통과할 때까지"를 `/goal`로 건다.
4. 그 세션이 자율로 도는 동안, 기능 작업 세션에 집중한다.
5. 둘 다 끝나면 각 브랜치를 합친다.

한 사람이 두 가지 일을 동시에, 충돌 없이, 한쪽은 자율로 끝냈다. 이게 2026-05
이후의 일하는 방식이다.

## 정리

- **Worktree** = 충돌 없이 가르기. **Agent View** = 가른 것 한눈에 보기.
- **/goal** = 조건 충족까지 자율. 단, 판정 가능한 조건으로.
- **Dynamic workflows** = 스크립트로 모는 대규모 병렬.
- 넷은 경쟁이 아니라 층위다. 규모와 자동화 수준에 따라 골라 쌓는다.

다음 장에서는 사람도 스크립트도 아닌 '시간'이 모는 자동화 — Monitor와
`/loop`로 만드는 자가 페이싱을 다룬다.
