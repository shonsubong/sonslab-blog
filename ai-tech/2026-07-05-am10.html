같은 문장이 토큰을 30% 더 쓴다 — Sonnet 5 토크나이저 교체의 셈법

AI 딥다이브 2026년 07월 05일 (일) · 10:00 · 7분 읽기
목차

  • 배경 (Why now)

TL;DR

  • Anthropic이 6월 30일 Claude Sonnet 5를 공개했다. 에이전트 작업 성능이 Opus 4.8에 근접하면서 가격은 입력 $3/출력 $15(8월 말까지 한시 $2/$10)를 유지한다.
  • 발표문 각주에 조용히 들어간 변화가 토크나이저 교체다. 같은 텍스트가 Sonnet 4.6 대비 약 30% 더 많은 토큰으로 쪼개지고, 언어별 편차도 커서 영어는 1.4배, 중국어는 거의 그대로라는 외부 측정이 나왔다.
  • 토큰당 단가는 그대로여도 토큰 수가 늘어 실질 요금은 달라진다. 8월 말까지의 한시 인하는 이 전환을 비용 중립으로 만들기 위한 장치다.

배경 (Why now)

6월 마지막 주는 프런티어 발표가 몰렸다. OpenAI가 26일 GPT-5.6 계열을 미국 정부 협의를 거친 제한 공개 형태로 미리 내놨고, Anthropic은 30일 Sonnet 5를 전 요금제에 풀었다. 포지션은 명확하다. Opus급 에이전트 성능을 Sonnet 가격에 — SWE-Bench Verified 85.2%, OSWorld-Verified 81.2%로 Sonnet 4.6을 큰 폭으로 앞선다 (Anthropic — Introducing Claude Sonnet 5; TechCrunch — Anthropic launches Claude Sonnet 5).

그런데 벤치마크 표보다 흥미로운 건 각주에 있던 한 문장이다. Sonnet 5는 새 토크나이저를 쓰고, 같은 입력이 콘텐츠 종류에 따라 1.0~1.35배 토큰으로 바뀐다는 것. Opus 4.7 때 이미 같은 교체가 있었는데 이번에 Sonnet까지 내려오면서 사실상 Anthropic 라인업 전체의 표준이 됐다. 토크나이저라는 눈금이 바뀌면 비용·문맥 창·출력 한도 계산이 전부 다시 필요하다.

핵심 메커니즘

토크나이저는 텍스트를 모델이 처리하는 정수 열로 바꾸는 앞단이다. BPE 계열은 말뭉치에서 자주 붙어 다니는 문자 쌍을 병합해 어휘집을 만들고, 어휘집이 특정 언어에 후할수록 그 언어는 짧은 토큰 열로 압축된다.

[텍스트] → [BPE 병합 규칙] → [토큰 ID 열] → [임베딩] → [Transformer]

구 토크나이저: "internationalization" → [international][ization]        (2토큰)
신 토크나이저: "internationalization" → [inter][national][ization]      (3토큰, 예시)

방향이 특이하다. 업계 흐름은 압축률을 올려 토큰 수를 줄이는 쪽인데 Anthropic은 반대로 갔다. 같은 텍스트가 더 많은 토큰이 되면 시퀀스가 길어지고 어텐션 연산과 KV 캐시도 함께 늘어난다. 그 비용을 감수하고 바꿨다는 건 잘게 쪼개는 것 자체가 모델 품질에 이득이었다는 뜻이다. 공식 설명은 "성능 개선을 위한 교체"가 전부고 설계 근거는 비공개다 (What's new in Claude Sonnet 5 — Claude Platform Docs). 밖에서 보이는 단서는 언어별 편차다. Simon Willison의 측정으로는 영어 1.4배, 스페인어 1.33배, 중국어 간체는 거의 1.0배였다 (@simonw — X). 영어에 몰아줬던 어휘 공간을 다른 언어와 코드 쪽으로 재배분했다고 읽는 게 자연스럽다. 다만 이건 외부 추정이고 정확한 설계는 확인이 필요하다.

코드 예시

같은 프롬프트를 두 모델의 count_tokens로 재보면 차이가 바로 드러난다.

import anthropic
client = anthropic.Anthropic()

prompt = open("my_system_prompt.txt").read()

for model in ["claude-sonnet-4-6", "claude-sonnet-5"]:
    n = client.messages.count_tokens(
        model=model,
        messages=[{"role": "user", "content": prompt}],
    )
    print(model, n.input_tokens)

# 출력 예:
#   claude-sonnet-4-6  41200
#   claude-sonnet-5    54800   (약 1.33배)

마이그레이션에서 실제로 걸리는 지점은 세 가지다. max_tokens를 출력 길이에 딱 맞게 잡아둔 워크로드는 같은 답변이 잘릴 수 있고, 1M 문맥 창은 토큰 기준으론 그대로지만 담기는 텍스트 양은 줄었고, 토큰 수 기준으로 짜둔 예산·캐시 코드는 전부 재측정 대상이다.

한계·반론

숫자부터 어긋난다. 공식 발표는 1.0~1.35배인데 외부 측정은 영어 기준 1.4배가 나온다. 어느 쪽이든 9월 1일 정가($3/$15) 복귀 후에는 영어 위주 워크로드의 실질 비용이 Sonnet 4.6보다 30~40% 올라간다. "토큰당 가격 동결"이라는 발표 문구와 실제 청구액 사이의 간극이다 (Simon Willison — What's new in Claude Sonnet 5). 한국어의 인플레이션 비율은 아직 신뢰할 만한 측정을 찾지 못했다. 직접 재보고 확인이 필요한 부분이다.

"드롭인 교체"라는 표현에도 유보가 붙는다. 파괴적 변경이 둘 있다. temperature/top_p/top_k를 기본값 외로 주면 400 에러가 나고, budget_tokens 방식의 수동 확장 추론도 제거되어 같은 에러를 돌려준다. 그리고 토크나이저가 다르면 "토큰당 비용" 비교 자체가 흔들린다. 모델 간 비교는 토큰 단가가 아니라 과제당 비용으로 해야 한다는 원칙이 이번 교체로 더 분명해졌다.

현직 엔지니어 관점

온디바이스 쪽에서 토크나이저는 늘 뒷전 취급이지만 실제로는 메모리 예산의 앞자리를 차지한다. 어휘집 크기가 임베딩 테이블과 출력층 크기를 결정하고, 토큰 인플레이션은 같은 문서를 처리할 때 KV 캐시 사용량을 그대로 키운다. 엣지 장비에서 토큰 30% 증가는 곧 캐시 메모리 30% 증가라 서버보다 타격이 직접적이다. 그런데도 프런티어가 연산 증가를 감수하고 교체를 택했다는 건, 토큰 효율보다 표현 품질이 우선순위가 됐다는 신호로 읽힌다. 개인적으로는 Claude Code 기본 모델이 Sonnet 5로 바뀌면서 같은 세션이 토큰을 더 쓰게 된 셈인데, 요금제 사용 한도를 함께 올렸다고 하니 체감 변화는 당분간 지켜볼 생각이다.
