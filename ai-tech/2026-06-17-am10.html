한 번에 256토큰을 칠한다 — DiffusionGemma가 메모리 병목을 연산으로 바꾼 방법

AI 딥다이브 2026년 06월 17일 (수) · 10:00 · 5분 읽기
목차

TL;DR

  • 구글 딥마인드가 6월 10일 공개한 DiffusionGemma 26B-A4B는 토큰을 하나씩 뱉지 않고, 256토큰짜리 "캔버스"를 한 번에 깎아 만드는 텍스트 확산 모델이다.
  • 핵심은 품질이 아니라 구조다. 자기회귀 디코딩의 메모리 병목을 연산 병목으로 바꿔, 단일 사용자 기준 H100 한 장에서 초당 1,000토큰을 넘긴다.
  • 활성 파라미터가 3.8B뿐이라 엣지에서도 노려볼 만하지만, 품질은 같은 체급 Gemma 4보다 낮고 아직 실험 단계다.

배경 (Why now)

자기회귀 모델은 토큰을 왼쪽에서 오른쪽으로 한 칸씩 채운다. 문제는 디코딩 구간이 연산이 아니라 메모리에 묶여 있다는 점이다. 한 토큰을 만들 때마다 모델 가중치를 메모리에서 연산기로 끌어와야 하는데, 이 적재 비용이 실제 계산보다 크다. 가중치는 배치 크기와 무관하게 한 번만 올리면 되니, 한 명을 위한 한 토큰이나 256명을 묶은 한 토큰이나 걸리는 시간이 거의 같다. 다중 사용자 처리량에는 좋지만, 혼자 쓰는 사람 입장에서는 연산기가 놀고 있는 셈이다.

6월 9일 Gemma 4가 나온 직후, 딥마인드는 같은 26B-A4B 백본을 확산용으로 미세조정한 DiffusionGemma를 같은 주에 풀었다. 텍스트 확산 모델을 공개 가중치로, 그것도 vLLM 지원까지 붙여 내놓은 건 이번이 사실상 처음이다. 노는 연산기를 단일 사용자 지연 단축에 돌려쓰자는 발상이 핵심이다.

핵심 메커니즘

이미지 확산은 가우시안 잡음에서 시작해 점점 지운다. 텍스트는 토큰이 이산값이라 그대로 옮기기 어렵다. DiffusionGemma는 [MASK] 토큰 대신 어휘에서 뽑은 무작위 토큰을 잡음으로 쓰는 Uniform State Diffusion을 택했다. 마스킹 방식은 한 번 채운 칸을 못 고치는데, 무작위 잡음 방식은 문맥이 바뀌면 이미 정한 토큰도 신뢰도가 떨어지는 순간 다시 잡음으로 되돌려 고칠 수 있다.

자기회귀(AR):  [t1]->[t2]->[t3]-> ... ->[t256]   (256스텝, 메모리 병목)

확산(Diffusion):
  canvas (무작위 256토큰)
     |   +-------------- 반복 --------------+
     v   v                                  |
  [예측: 캔버스 전체를 동시에 추정]          |
     |                                       |
  [리마스킹: 저신뢰 토큰만 무작위로 재오염]--+
     |
     v   (15~20스텝)
  확정된 256토큰 블록 -> KV캐시에 append -> 다음 블록

한 백본이 두 모드를 오간다. 인과 어텐션으로 프롬프트를 KV캐시에 채우는 선적재(prefill) 단계, 그리고 양방향 어텐션으로 캔버스 전체를 동시에 깎는 디노이즈 단계다. 캔버스 하나가 256토큰으로 고정이라, 긴 글은 한 블록을 끝내 KV캐시에 붙이고 새 캔버스를 다시 시작하는 블록 확산으로 이어 붙인다.

코드 / 의사코드

# Uniform State Diffusion 디코딩 (의사코드)
canvas = sample_random_tokens(n=256)      # 어휘에서 무작위 초기화
kv = prefill(prompt)                       # 인과 어텐션으로 문맥 선적재

for step in range(num_steps):              # 보통 15~20회
    # 예측: 양방향 어텐션으로 캔버스 전체를 한 번에 추정
    logits = denoise(canvas, kv, attn="bidirectional")
    probs  = softmax(logits)
    pred   = argmax(probs, axis=-1)
    conf   = probs.max(axis=-1)            # 위치별 신뢰도

    # 리마스킹: 신뢰도 낮은 위치만 무작위 토큰으로 다시 오염
    keep   = conf >= threshold(step)       # 스텝이 갈수록 임계값 완화
    canvas = where(keep, pred, sample_random_tokens())

kv = append_block(kv, canvas)              # 확정 블록을 KV캐시에 적재

스텝당 15~20토큰이 확정되니, 256토큰을 15~20스텝이면 마무리한다. 자기회귀의 256스텝과 비교하면 순방향 횟수가 한 자릿수 배 줄어든다.

한계·반론

속도 숫자는 솔깃하지만 함정이 있다. 첫째, 품질이 같은 체급 Gemma 4보다 낮다. 스텝을 적게 줄이면 더 떨어진다. 구글도 품질이 중요한 작업엔 표준 Gemma 4를 권하고, DiffusionGemma는 실험 등급으로 분류했다. 둘째, 연산 병목으로의 전환은 배치가 작을 때만 이득이다. 서버에서 수백 명을 묶어 돌리는 상황에선 자기회귀의 처리량 우위가 그대로 살아 있다. 셋째, 캔버스 256토큰 고정과 블록 이어 붙이기 구조라, 블록 경계를 넘는 일관성·정정 능력은 더 검증이 필요하다. "초당 1,100토큰"은 H100·FP8·저배치라는 조건이 붙은 수치이며, 조건이 바뀌면 그림이 달라진다.

현직 엔지니어 관점

메모리 병목을 연산 병목으로 옮긴다는 한 줄이 이 모델의 전부이자, 온디바이스 관점에서 가장 흥미로운 지점이다. 엣지 NPU는 연산 처리량은 받쳐주는데 메모리 대역폭이 부족해 자기회귀 디코딩에서 늘 굶주린다. 토큰을 묶어 한 번에 처리하면 가중치 적재 1회를 여러 토큰이 나눠 쓰니, 대역폭당 토큰 효율이 올라간다. 활성 3.8B에 양방향 어텐션이라는 점도 정적 컴파일·배치 스케줄링에 유리하다. 다만 양방향 어텐션은 KV캐시 재사용 패턴이 자기회귀와 달라 캐시 설계를 다시 봐야 하고, 256토큰 캔버스를 한 번에 올릴 SRAM·온칩 버퍼 여유가 엣지에서 충분한지는 칩마다 따져봐야 한다. 결론을 내긴 이르고, 저배치 단일 사용자 시나리오에 한해 실측해볼 가치는 분명하다.
