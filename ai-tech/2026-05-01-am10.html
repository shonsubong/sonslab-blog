MXFP4 — 4비트 부동소수점이 INT4를 밀어낸 이유

TL;DR

  • MXFP4는 OCP가 표준화한 4비트 부동소수점(E2M1) + 32원소 블록당 공유 스케일(E8M0)을 결합한 microscaling 포맷이다.
  • 같은 4비트 예산에서 INT4 대비 outlier 채널 회복률이 훨씬 좋아, LLM 추론에서 FP16 대비 메모리·대역폭을 약 4배 줄이면서 정확도 손실은 1~2% 수준으로 보고된다.
  • Blackwell·MI355X 텐서코어가 1차 시민으로 지원하고, vLLM·PyTorch가 stable로 승격하면서 추론 디폴트 자리에 들어왔다.

배경 — 왜 지금 다시 4비트인가

INT4 양자화는 GPTQ 시절부터 익숙하다. 그런데 정작 production 추론에서 디폴트가 되지 못한 이유는 단 하나, outlier 채널이었다. 채널별 스케일을 잡아도 한두 개 튀는 활성값이 양자화 격자를 다 잡아먹어 정확도가 무너졌다.

MXFP4는 두 가지를 바꿨다. 먼저 4비트 자체를 부동소수점(E2M1, 지수 2비트 + 가수 1비트)으로 바꿔 동적 범위를 넓혔다. 그리고 NVIDIA Blackwell과 AMD MI355X가 텐서코어 차원에서 MXFP4 dot product를 하드웨어 1차 시민으로 지원하면서 GEMM throughput이 FP16의 4배 가까이로 올라왔다 (NVIDIA Blackwell 아키텍처 페이지).

지난 두 주 사이의 트리거 사건은 두 개다. vLLM 0.9가 MXFP4 가중치 + KV 캐시 옵션을 stable로 올렸고, PyTorch 2.7이 torch.float4_e2m1 dtype을 안정 채널에 합쳤다. 양자화가 라이브러리 트릭에서 "데이터 타입"으로 한 칸 올라온 것이다 (PyTorch 2.7 release notes).

핵심 메커니즘 — 32원소 마이크로스케일

MXFP4는 OCP Microscaling Formats(MX) 명세 위에 얹혀있다 (OCP MX v1.0 Spec).

[블록 = 32 elements]
 ┌────────────────────────────────────────────────┐
 │ scale (E8M0, 8bit)  ×  element (E2M1, 4bit) ×32│
 └────────────────────────────────────────────────┘
       ▲                       ▲
   블록 공유 스케일       32개 4비트 부동소수

평균 비트수 = (8 + 32 × 4) / 32 = 4.25 bit/element

블록 단위 공유 스케일이 핵심이다. 텐서 전체에 스케일 하나를 쓰는 per-tensor 양자화가 outlier 한두 개에 눌렸던 반면, 32원소마다 스케일을 새로 잡으면 outlier 영향이 자기 블록 안에서 끝난다. 스케일은 E8M0 — 지수만 8비트로 들고 있는 power-of-two 포맷이라, dequant은 시프트 연산 한 번이면 된다.

E2M1 자체의 표현 가능 값은 {±0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6}로, INT4의 {-8...7} 균등 격자보다 0 근처가 촘촘하다. LLM activation 분포가 0 부근에 몰리는 통계와 정확히 맞물린다는 게 핵심이다.

코드 — MXFP4 quantize 의사코드

def quantize_block_mxfp4(x_block):  # x_block: shape (32,), fp16/bf16
    # 1. 블록 absmax → power-of-two scale
    amax = x_block.abs().max()
    scale_exp = ceil(log2(amax / 6.0))   # 6.0 = E2M1의 최대 표현값
    scale = 2.0 ** scale_exp             # E8M0 (지수 8bit)로 저장

    # 2. element-wise: 정규화 후 가장 가까운 E2M1 값으로 라운드
    normalized = x_block / scale
    e2m1 = round_to_e2m1(normalized)     # {±0,±.5,±1,±1.5,±2,±3,±4,±6}

    return scale_exp, e2m1                # 8bit + 32×4bit = 136bit / block

def dequantize_block(scale_exp, e2m1):
    return e2m1 * (2.0 ** scale_exp)     # 시프트 한 번

vLLM에서는 한 줄이면 추론까지 간다.

vllm serve meta-llama/Llama-3.3-70B \
  --quantization mxfp4 --kv-cache-dtype mxfp4

한계·반론

  • 추론 한정이 안전 영역이다. Forward/backward 모두 MXFP4로 돌리는 학습은 변동성이 커서 수렴 불안정이 보고된다. 학습은 여전히 BF16 / FP8 mix가 기본이다 (NVIDIA Transformer Engine 문서).
  • 캘리브레이션 데이터에 민감하다. 도메인 시프트가 큰 추론 — 코드↔자연어, 한국어↔영어 — 에서는 wikitext 캘리브레이션 한 번만으로 부족하다. task-specific calibration을 별도로 돌려야 정확도 회복률이 광고치에 근접한다.
  • 여전히 mixed-precision fallback이 필요한 layer가 남는다. Attention output projection·embedding layer는 outlier 분포가 극단적이라 INT8 / FP8로 빠지는 게 일반적이라는 분석이 나온다 (@dylan522p — SemiAnalysis). "MXFP4 single-format" 마케팅을 그대로 받지 말 것.

현직 엔지니어 관점

산업 비전 inference 입장에서 보면, MXFP4는 "70B 모델을 24GB 데스크톱 GPU에서 실용적으로 돌릴 수 있는 문턱"을 처음 넘겨준 양자화 포맷이다. Llama-3.3 70B를 기준으로 가중치만 비교하면 FP16 약 140GB, INT4 약 35GB, MXFP4 약 37GB(블록 스케일 포함)로 INT4와 거의 같은 풋프린트를 쓰면서 정확도 회복률은 한참 위에 있다. 온디바이스 NPU 쪽에서도 OCP MX 호환을 명시하는 칩이 늘고 있어, "같은 가중치 파일을 GPU↔NPU에 그대로 이식"이 현실 옵션이 된다. 산업용 vision pipeline처럼 모델 사이즈가 메모리에 발목 잡혀 있던 영역이 가장 먼저 수혜를 본다 (@karpathy의 4비트 추론 노트). 다만 트레이닝·파인튜닝은 BF16을 유지하고 추론만 MXFP4로 떨어뜨리는 두 단계 파이프라인이 당분간 표준일 것이다 — 학습 안정성과 배포 효율을 한 데이터 타입으로 합치려는 시도는 아직 이르다.
