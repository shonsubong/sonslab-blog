코드를 진화시켜 데이터센터 0.7%를 되찾았다 — AlphaEvolve 1년 보고서

AI 딥다이브 2026년 06월 01일 (월) · 10:00 · 7분 읽기
목차

  • 배경 — 왜 지금인가

TL;DR

  • DeepMind가 5/19 Google I/O에 맞춰 발표한 AlphaEvolve 1년 임팩트 보고서에서, Borg 스케줄링 휴리스틱 한 줄이 Google 전체 컴퓨트의 평균 0.7%를 1년 넘게 회수해 왔다는 사실이 공개됐다 (DeepMind — AlphaEvolve impact).
  • 같은 시스템이 FlashAttention 커널 런타임을 최대 32.5% 줄였고, Gemini 학습용 핵심 커널을 23% 가속해 전체 학습 시간을 1% 단축했다.
  • 핵심은 모델 자체가 아니라 "LLM 변이 + 결정론적 평가자 + 진화 선택" 루프를 일반 코드 공간에 적용한 점이다. 한 번의 forward pass가 아니라 수천 시간 분량의 자동 실험을 돌리는 구조다.

배경 — 왜 지금인가

5월 19일 Google I/O에서 Pushmeet Kohli 부사장이 AlphaEvolve의 1년 운영 결과를 공개했다. 처음 등장한 2025년 5월에는 "수학·알고리즘 발견용 연구 프로토타입" 정도로 받아들여졌고, 4×4 복소수 행렬곱에서 56년 묵은 Strassen 변형을 깬 게 헤드라인이었다. 그 사이 시스템은 사이언스 PR을 벗어나 Borg 스케줄러, Gemini 학습 파이프라인, TPU/Verilog 회로, 양자 회로 컴파일, DNA 시퀀싱 보정까지 다섯 영역에서 실제 프로덕션에 들어갔다 (blog.google — AlphaEvolve updates).

특히 PacBio와의 협업에서 DeepConsensus의 변이 검출 오차가 30% 줄었다. PacBio는 같은 흐름에서 HiFi 인간 게놈 한 건당 비용을 345 USD까지 내렸다 (PacBio — HiFi sequencing accuracy). 양자 쪽에서는 Willow 프로세서용 회로의 게이트 오차를 10배 낮춰 분자 시뮬레이션 데모를 가능하게 했다. "에이전트가 자기 코드를 고친다"는 카테고리가 같은 주에 한꺼번에 산업 의제로 올라왔다.

핵심 메커니즘

AlphaEvolve는 모델이 아니라 루프다. 핵심 구성요소 세 가지가 비동기로 맞물려 돈다.

                  ┌──────────────────────┐
                  │   Program Database   │ ← 후보 코드 + 점수
                  └──────────┬───────────┘
                             │ 점수 가중 샘플링
                             ▼
   ┌─────────────┐   Prompt   ┌─────────────────┐
   │ Gemini Flash│ ←──────────│ Prompt Sampler  │
   │ Gemini Pro  │            └─────────────────┘
   └──────┬──────┘
          │ 변이된 diff
          ▼
   ┌─────────────────┐  실행/측정  ┌──────────────┐
   │   Evaluator     │ ──────────→ │ Score 벡터   │
   │ (결정론적 함수) │              └──────┬───────┘
   └─────────────────┘                     │
                                           ▼
                                  Program Database 갱신

Prompt Sampler는 데이터베이스에서 부모 후보를 뽑아 "이 코드를 더 빠르게" 같은 목표 + 평가 함수 시그니처를 컨텍스트에 끼워 Gemini에게 던진다. Flash는 폭, Pro는 깊이를 담당하고, 출력은 부분 diff부터 모듈 전체 재작성까지 가변이다. Evaluator는 사용자가 작성한 결정론적 함수가 후보를 실제로 실행해 속도·정확도·면적 등 다수 지표를 매긴다. 진화 알고리즘은 이 벡터를 보고 다음 부모를 고른다.

핵심 차별점은 평가자가 결정론이라는 것이다. LLM이 "이 코드가 더 빠를 거예요"라고 환각해도 컴파일·실행 결과가 거짓을 걸러낸다. 그래서 변이 엔진의 추론 정확도가 떨어져도 시스템 전체는 단조 개선을 유지한다.

코드 / 의사코드

전체 루프를 30줄 의사코드로 줄이면 이렇다.

def alphaevolve(seed_program, evaluator, budget):
    db = ProgramDB()
    db.add(seed_program, score=evaluator(seed_program))

    for step in range(budget):
        # 1) 점수 가중 샘플링으로 부모 k개 추출
        parents = db.sample(k=2, temperature=0.7)
        prompt  = build_prompt(parents, evaluator.signature)

        # 2) Flash/Pro 앙상블 변이
        model = gemini_flash if step % 4 else gemini_pro
        child = apply_diff(parents[0], model.generate_diff(prompt))

        # 3) 결정론적 평가 — 실패는 폐기
        try:
            score = evaluator(child)         # 벡터 가능
        except (CompileError, Timeout, WrongAnswer):
            continue

        # 4) Pareto 수용
        if db.dominates_any(score):
            db.add(child, score)

    return db.best()

실제 운영에서는 evaluator가 분산 클러스터에서 수십 분에서 수 시간씩 돌고, db는 island 모델로 다양성을 유지한다. FlashAttention 사례에서 evaluator는 H100 한 장에서 실측 토큰/초를 재고, Verilog 사례에서는 합성 후 면적·지연을 본다.

한계·반론

낙관 일색이 아니다. 우선 evaluator를 짜는 게 어렵다. "정답을 점수로 표현 가능한 문제"에만 적용되고, 미분 불가능하거나 평가 비용이 큰 문제는 사실상 막힌다. DeepMind가 공개한 사례도 결국 (1) 정답이 명확한 알고리즘 문제, (2) 실측 가능한 시스템 코드(커널·스케줄러·회로), (3) 통계 메트릭이 있는 모델 보정 정도다. 일반 애플리케이션 코드처럼 "이게 더 좋은가"가 모호한 영역에는 그대로 끌고 오지 못한다.

비용 의문도 있다. Borg 0.7% 회수가 인상적이지만, 그 결과에 도달하기 위해 회전한 Gemini 추론·후보 실행 비용은 보고서에 공개되지 않았다. 0.7%가 운영 비용을 능가했다는 직접 증거 없이 "회수율"만 강조된다는 지적이 나온다 (VentureBeat — Meet AlphaEvolve). 진화 알고리즘 자체는 1960년대 개념이고 새로운 건 LLM 변이 엔진뿐인데, 평가자·인프라가 Google급이 아니면 같은 비율의 이득을 기대하기 어렵다는 의심도 함께다.

Verilog 회로 사례에서 "불필요한 비트를 제거했다"는 표현도 모호하다. 어떤 검증 체계로 등가성을 보장했는지(SMT 증명? 시뮬레이션 커버리지?) 디테일이 공개되지 않아, 같은 방법을 사내 RTL에 적용하려면 안전성 보장은 별도 작업이 된다.

현직 엔지니어 관점

내가 일하는 영역으로 가져오면, AlphaEvolve의 진짜 의미는 "커널·스케줄러 같은 측정 가능한 코드층이 LLM 자동화의 1차 표적이 됐다"는 점이다. CUDA·Triton 커널, FPGA HLS, 메모리 할당기, 컴파일러 패스 — 결정론적 벤치마크가 있는 곳은 같은 루프로 갈아탈 수 있다. 온디바이스 NPU의 라이브러리 튜닝, 영상 파이프라인의 ISP 알고리즘 같은 도메인은 이미 "사람이 며칠 갈아 1~3% 짜내던 영역"인데, evaluator만 잘 짜면 무인 운영이 가능해진다. 다만 평가자 작성과 회귀 검증 인프라가 본질이고 LLM은 그 위에 얹는 변이 엔진이라는 점은 변하지 않는다. 코드를 자동으로 진화시키는 시대에도 결국 일은 "평가 함수를 정확하게 정의하는 사람"에게 남는다.
