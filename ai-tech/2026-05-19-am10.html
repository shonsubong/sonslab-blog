LLM 데이터센터가 물·탄소를 함께 줄인 길 — MARLIN이 추론에 게임이론을 끼운 방식

AI 딥다이브 2026년 05월 19일 (화) · 10:00 · 5분 읽기
목차

TL;DR

  • 추론은 LLM 수명주기 에너지의 90%를 먹는다. 학습 한 번보다 매일 흐르는 추론이 데이터센터의 진짜 부담이다.
  • HPE Labs·CSU가 5월 13일 공개한 MARLIN(arXiv 2605.13496)은 라우터·모델 선택·GPU 배치·쿨링을 각자 RL 에이전트로 풀어 게임이론적 균형을 찾는다.
  • 기존 SOTA 대비 TTFT 18%, 탄소 33%, 물 43%, 전기 11%를 동시에 줄였다. 추론 스케줄러가 단일 목표에서 다목표 협상으로 넘어가는 첫 실용 결과.

배경 (Why now)

데이터센터 환경 부담이 산업 의제로 넘어온 게 지난 12개월이다. 글로벌 데이터센터는 연 200TWh를 넘겼고, 추론 단독으로 2027년 100TWh가 예측된다. LLM 요청 20~50건이 냉각수 500mL을 증발시킨다는 추정도 보편화됐다(How Hungry is AI — arXiv:2505.09598).

문제는 기존 스케줄러들이 한쪽만 본다는 점이다. vLLM·TGI 라우터는 TTFT/처리량만, 쿨링은 facility 쪽이 PUE 1.1만 본다. carbon-aware 라우팅은 PV 발전이 비는 야간에 일을 몰고, water-efficient 라우팅은 외기 온도가 높은 지역을 피한다 — 저탄소 그리드가 물 부족 지역과 겹칠 때 두 정책은 충돌한다.

5월 13일 arXiv의 MARLIN은 이 충돌을 비협력 게임 균형 탐색으로 푼다(Moore et al. — arXiv:2605.13496). 한 달 전 SLIT가 단일 정책으로 4축을 묶으려다 한계를 본 자리에 멀티에이전트 분해로 응답한 셈이다(SLIT — arXiv:2505.23554).

핵심 메커니즘

MARLIN은 추론 파이프라인을 4개 결정 지점으로 잘라, 각 지점에 독립 RL 에이전트를 둔다.

[들어오는 요청 큐]
       ↓
┌────────────────────────────────────────────┐
│ A. 라우터       (지연 vs 큐 길이)            │ ─┐
│ B. 모델 선택    (정확도 vs FLOP)             │ ─┤  Nash 균형
│ C. 클러스터 배치 (전력 vs 처리량)            │ ─┤  탐색
│ D. 쿨링 컨트롤  (물 증발 vs T_chip)          │ ─┘
└────────────────────────────────────────────┘
       ↓
[공동 액션: 어떤 모델을 어디서, 몇 W로, 얼만큼 식혀서]

핵심은 세 가지다. 보상이 단일 스칼라가 아니라 (TTFT, CO₂, H₂O, $) 벡터로, 가중합 대신 Pareto 전선을 직접 학습한다. 에이전트들은 동시에 행동하지만 서로의 보상을 부분 관측한다 — 라우터는 쿨링이 한계에 가까운지만 신호로 받는다. 학습은 자기 보상만 보는 단독 PPO 워밍업 → multi-agent PPO 균형 수렴의 두 단계로 나뉘는데, 단일 PPO로 모든 결정을 묶었던 SLIT보다 학습 안정성이 좋다고 ablation에서 보고한다.

코드 / 수식 예시

보상 합성은 "가장 뒤처진 축"에 페널티를 거는 형태다.

# MARLIN reward shaping (의사 코드)
def joint_reward(state, action, baseline):
    ttft   = baseline.ttft / state.ttft       # ↑ 좋음
    carbon = baseline.co2  / state.co2        # ↑ 좋음
    water  = baseline.h2o  / state.h2o        # ↑ 좋음
    energy = baseline.kwh  / state.kwh        # ↑ 좋음

    metrics = [ttft, carbon, water, energy]
    worst   = min(metrics)
    mean    = sum(metrics) / 4
    # Pareto-소외 페널티: 평균-최저 격차를 보정
    return mean - 0.5 * (mean - worst)

각 에이전트의 PPO objective엔 cross-agent KL 항이 붙어, 한쪽이 독주하면 다른 에이전트들이 보상 추정치를 끌어내리도록 묶인다. 4개 에이전트 환경에서 약 80K step에 ε-Nash 균형이 안정화됐다.

한계·반론

첫째, 시뮬레이션 의존이 크다. 18/33/43/11%는 H100 클러스터 + Google Cloud 트레이스 + 4개 지역 외기 온도를 합성한 환경의 결과지 실 프로덕션 측정이 아니다. SLA·테넌트 격리가 끼면 자유도가 절반 이하로 줄어든다. 둘째, 게임이론 균형은 단일 최적해보다 수렴이 느리다 — 부하 급변 시점(아침 9시 트래픽 점프)에 잠시 발산하는 모습이 ablation에 보인다. 셋째, "왜 이 요청이 멜버른으로 갔나"를 사람에게 설명하기 어렵다. 외부 트래픽 조작으로 특정 지역에 부하를 몰 수 있다는 점도 Insider Attacks on Multi-Agent LLM 흐름과 닿는다.

현직 엔지니어 관점

반도체 라인의 오래된 룰 "열은 곧 수율"이 데이터센터 GPU 클러스터에 그대로 옮겨붙는다 — chip junction 온도 5℃ 상승은 워크로드 전력 8~12% 증가, 쿨링 가동률 증가, 물 증발 비례 증가로 이어진다. MARLIN의 처방은 이 비선형 결합을 단일 보상으로 묶지 않고 에이전트들이 협상하게 둔다는 데 있다. 모바일 NPU에도 같은 그림이 작동한다 — 쿨링이 없으니 전력→발열→throttling 되먹임이 더 빠르게 돈다. 보상 정규화 처방은 단말 SoC 거버너에도 옮길 만하다. 다만 SLA 99.9% 양산 워크로드에선 ε-Nash 출렁임이 받아들여지지 않는다. 클라우드 다중 테넌트가 먼저, 단일 사이트는 뒤늦게 따라올 그림이다.
