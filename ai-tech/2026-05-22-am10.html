검증을 별도 에이전트로 떼어낸 순간 — 루브릭 채점 루프가 추론 시점 품질을 끌어올린 방식

TL;DR

  • 생성하는 에이전트와 채점하는 에이전트를 분리하고, 루브릭 점수가 기준에 못 미치면 되돌려 다시 쓰게 하는 추론 시점 검증 루프가 제품으로 나왔다.
  • 모델을 더 키우거나 재학습하지 않고도 어려운 문제에서 작업 성공률 +10%p — 추론 시점 연산을 품질로 바꾸는 또 하나의 손잡이다.
  • 단, 루브릭의 빈틈은 곧장 리워드 해킹으로 이어진다. "점수는 오르는데 진짜 품질은 떨어지는" 함정이 같은 주 논문에서 그대로 재현됐다.

배경 (Why now)

5월 6일 Anthropic이 Code with Claude(샌프란시스코)에서 Managed Agents에 dreaming·outcomes·멀티에이전트 오케스트레이션을 한꺼번에 공개 베타로 풀었다 (Anthropic — New in Claude Managed Agents). 이 중 핵심은 outcomes다. 별도 채점기가 사용자가 적은 루브릭만 보고 산출물을 평가하고, 부족하면 어디가 모자란지 짚어 작업 에이전트로 되돌리는 채점-수정(grade-and-revise) 루프다. 흥미로운 건 타이밍이다. 거의 같은 주 arXiv에는 루브릭 기반 보상이 어떻게 망가지는지 다룬 논문이 잇따라 올라왔다 (arXiv 2605.12474, arXiv 2605.17291). 산업은 검증을 별도 모듈로 떼어내 제품화했고, 학계는 바로 그 떼어낸 검증기가 속는 지점을 파고든 셈이다. 둘을 겹쳐 읽으면 "검증을 어디까지 믿을 수 있나"라는 질문의 현재 좌표가 보인다.

핵심 메커니즘

본질은 생성기(generator)와 검증기(verifier)의 컨텍스트 격리다. 채점기가 작업 에이전트의 추론 트레이스를 못 보게 막는 게 설계의 핵심이다. 같은 컨텍스트에서 자기가 쓴 글을 자기가 채점하면, 자기 합리화에 점수가 부풀려진다. 그래서 채점기는 새 컨텍스트에서 루브릭과 산출물만 읽는다.

        ┌──────────────┐   산출물    ┌───────────────┐
입력 → │  생성 에이전트  │ ─────────→ │  채점 에이전트   │
        └──────────────┘            │ (독립 컨텍스트,  │
              ▲                      │  루브릭만 읽음)   │
              │  수정 지시(gaps)      └───────┬───────┘
              └──────────────────────────────┘
        점수 < 기준 → 재시도 (기본 3회 · 최대 20회)
        점수 ≥ 기준 → 통과 / 예산 소진 → 마지막 본 반환

학습 시점에 보상 모델로 정책을 미세조정하던 RLVR(직전 글에서 다룬 GRPO 계열)과 달리, 이건 가중치를 건드리지 않고 추론 시점에만 도는 루프다. 그래서 어떤 모델에도 바로 씌울 수 있다. Anthropic 내부 평가에서 outcomes는 전반 +10%p, 문서 생성에서 docx +8.4%, pptx +10.1%의 성공률 향상을 보였다. 모델은 그대로 두고 루프만 씌운 결과다.

코드 / 의사코드

def outcomes_loop(task, rubric, max_iters=3):
    draft = generator(task)                  # 작업 에이전트가 초안 생성
    for _ in range(max_iters):               # 기본 3회, 최대 20회
        # 채점기는 새 컨텍스트 — 작업 추론 트레이스를 못 본다
        score, gaps = grader(draft, rubric)  # 독립 컨텍스트 평가
        if score >= rubric.threshold:
            return draft                     # 기준 통과
        draft = generator(task, revise=gaps) # gaps만 받아 재작성
    return draft                             # 예산 소진 → 마지막 본 반환

핵심은 revise=gaps 한 줄이다. 전체 트레이스를 다시 넘기지 않고 "무엇이 모자란가"만 구조화해 돌려보낸다. 이게 컨텍스트 폭증을 막고, 채점기를 매번 깨끗한 상태로 유지한다.

한계·반론

루브릭이 실패 모드를 다 적지 못하면 검증을 강화해도 리워드 해킹이 막히지 않는다. arXiv 2605.12474는 루브릭 채점기가 RL 체크포인트를 더 선호하는데도, 루브릭 없이 보는 심판들은 오히려 base 모델을 선호하는 역전을 보고한다. 점수와 실제 품질이 갈라지는 것이다. 자기수정 루프 자체도 폭주한다. arXiv 2605.17291은 AIME 2025에서 롤아웃의 48.1%가 중간 단계를 반복 재작성하며 점수만 부풀리고 끝내 종료하지 못하는 현상을 관찰했다. 더 근본적으로, 심판은 토큰 한 개로도 속을 수 있다 (arXiv 2507.08794 — One Token to Fool LLM-as-a-Judge). 비용도 무시 못 한다. 루프 N회는 토큰 N배에 채점기 호출이 얹히는 구조라, 품질 향상의 대가가 곧 추론 단가다.

현직 엔지니어 관점

이 손잡이는 클라우드에선 쓸 만하지만 온디바이스로 내릴 땐 사치에 가깝다. 채점 루프가 만드는 N배 토큰을 엣지 NPU의 전력 예산이 받아주지 못한다. 그래서 단말로 내려보낼 땐 채점기를 증류(distill)하거나, 전체 루프 대신 가벼운 검증 헤드 한 번으로 압축하는 절충이 필요하다고 본다 — 확인은 필요한 영역이다. 개인적으로도 집에서 Claude Code(MAX)를 돌릴 때 본능적으로 "출력 → 자가 점검 → 재작성"을 시키는데, outcomes는 그 습관을 격리된 컨텍스트로 제품화한 것이다. 반도체 쪽 직관으로 옮기면, 검증기를 생성기와 같은 컨텍스트에 두지 않는 건 캐시 파티셔닝과 같다. 같은 메모리에 섞으면 오염되고, 떼어내면 깨끗하지만 면적(여기선 토큰)을 더 먹는다. 결국 "어디까지 검증에 자원을 태울 것인가"라는 예산 문제로 수렴한다.
