1M 컨텍스트 시대의 옆문 — TTT-E2E가 어텐션 위에 학습 루프를 얹은 방식

AI 딥다이브 2026년 05월 29일 (금) · 10:00 · 6분 읽기
목차

  • 배경

TL;DR

  • Anthropic이 어제(5/28) Opus 4.8에 1M 토큰 컨텍스트를 디폴트로 켰고, 1M을 어떻게 끌고 가느냐가 이번 주 추론 인프라의 본질 문제로 다시 떠올랐다.
  • TTT-E2E는 새 백본을 만들지 않고, 표준 Transformer + 슬라이딩 윈도우 어텐션 위에 추론 시점 next-token 학습 루프 한 겹을 더 얹어 컨텍스트를 가중치에 압축한다.
  • 3B 모델·H100 기준으로 128K에서 풀 어텐션 대비 2.7배, 2M에서 35배 빠르면서 손실은 풀 어텐션과 같은 기울기로 스케일링한다.

배경

어제(5/28) Anthropic이 Claude Opus 4.8을 공개하면서 1M 토큰 컨텍스트를 API 디폴트로 켰다 (Anthropic). 같은 흐름에서 NVIDIA 기술 블로그가 작년 12월 arXiv에 올라간 TTT-E2E를 다시 전면에 꺼냈다 (NVIDIA). 1M 디폴트가 "실제로 돌아간다"는 그림이 풀 어텐션 위에서는 성립하지 않는다는 신호가 같이 따라왔다.

기존 풀 어텐션은 KV 캐시가 토큰 수에 선형으로 늘고, 토큰당 비용도 컨텍스트 길이에 비례한다. 1000만 번째 토큰을 처리하는 비용이 10번째 토큰의 100만 배라는 수식이, 1M 시대에는 더 이상 종이 위 농담이 아니다. Mamba 2·Gated DeltaNet 같은 RNN 계열은 토큰당 비용을 상수로 묶었지만, 컨텍스트가 길어질수록 손실이 풀 어텐션과 벌어진다. TTT-E2E는 "둘 다 잡는 첫 번째 방법"이라는 자리를 노린다.

핵심 메커니즘

본질은 "Mamba 같은 새 백본을 만들지 말고, 표준 Transformer를 그대로 두되 추론 시점에 학습 루프 한 겹을 더 얹자"는 입장이다.

[입력 컨텍스트]
      │
      ▼
┌────────────────────────────────┐
│ Transformer + Sliding-Window   │  ← 토큰당 상수 비용
└──────┬─────────────────────────┘
       │ inner loop: next-token CE
       ▼
   fast weights in-place 업데이트 (TTT)
       │
       ▼
[출력 토큰]

두 루프가 분리돼 있는 게 핵심이다. 내부 루프는 추론 중에 주어진 컨텍스트로 다음 토큰 예측 손실을 흘려 빠른 가중치(fast weights)를 갱신한다. 외부 루프는 사전학습 단계에서 "TTT 이후의 최종 손실"을 메타학습으로 최적화해, 모델이 처음부터 TTT에 적합한 초기화 상태로 출발하도록 만든다 (arXiv 2512.23675). 풀 어텐션의 KV 캐시처럼 모든 토큰을 보관하지 않고도, 압축된 핵심 정보가 가중치 안에 들어간다.

코드 예시

공식 저장소(test-time-training/e2e)의 추론 루프를 단순화하면 이렇다.

# 의사코드
fast_weights = init_from_meta_pretraining()

for chunk in stream_context(context, window=W):
    # 내부 루프: 컨텍스트로 next-token 학습
    logits = model(chunk, fast_weights)
    loss = next_token_ce(logits, chunk[1:])
    grads = torch.autograd.grad(loss, fast_weights)
    fast_weights = inner_update(fast_weights, grads, lr_inner)

# 학습된 fast weights로 실제 응답 생성
output = generate(prompt, fast_weights)

fast_weights는 모델 전체가 아니라 일부 파라미터다. In-Place TTT 계열은 MLP 블록의 최종 projection 행렬을 빠른 가중치로 쓰는 것을 표준으로 잡는다 (arXiv 2604.06169). 메타학습된 초기화 덕분에 짧은 추론 루프만으로도 의미 있는 압축이 일어난다. 760M 베이스라인 대비 hidden state는 5배 크지만(88M vs 18M), H100 prefill 지연은 절반(0.0086 vs 0.017초/1K 토큰)이라는 게 NVIDIA가 공개한 수치다.

한계·반론

사전학습 비용이 비싸다. 메타학습은 gradients of gradients를 요구하는데, FlashAttention 표준 API가 2차 미분을 지원하지 않아 8K 짧은 컨텍스트에서도 일반 사전학습 대비 3.4배 느리다. 커스텀 어텐션 커널이 필요하거나, 사전학습된 표준 Transformer에서 워밍업하는 하이브리드 초기화가 차선책이다.

디코딩 중 가중치가 변하므로 같은 배치 안에서 사용자별로 가중치를 분리하는 서빙 스택이 필요해진다. vLLM처럼 KV 캐시만 잘라 멀티테넌트를 풀던 가정이 깨진다.

"긴 컨텍스트를 잊지 않는다"는 주장은 무손실 회상이 아니라 압축이다. 정확한 토큰 인용이 필요한 워크로드(코드 diff 추적, 법률·계약 인용)는 여전히 RAG와 풀 어텐션을 함께 끌고 가야 한다. 저자들도 "RAG는 메모장, TTT는 두뇌"라는 표현으로 분리 자체는 인정한다.

현직 엔지니어 관점

온디바이스 NPU에서 1M을 다루는 시나리오에서 이 접근의 가치가 가장 크다. KV 캐시가 토큰 수에 선형으로 늘면 LPDDR 대역폭이 먼저 죽고, 1M은커녕 128K도 모바일에서는 KV가 모델 크기를 넘는다. TTT-E2E는 토큰당 비용을 상수로 묶으면서 손실 곡선은 풀 어텐션처럼 가져가니, 메모리 대역폭이 빠듯한 모바일 칩의 가장 큰 약점을 정확히 가린다.

다만 NPU 컴파일러가 추론 중 가중치 갱신을 자연스럽게 받아주지 않는 게 현실적 장벽이다. 보통 NPU 그래프는 가중치를 상수로 고정해 INT4·INT8로 양자화하는데, fast weights만 부분적으로 FP16으로 풀어두고 in-place 업데이트를 허용하는 mixed-precision 스케줄이 별도로 필요하다. 양자화팀과 컴파일러팀이 같이 들어가야 할 작업이다. 현 시점에서는 클라우드 H100 추론에서 먼저 검증한 뒤, 2026년 하반기 모바일 NPU 펌웨어가 받쳐줄 때 두 번째 파도가 올 가능성이 있다고 본다. 확인 필요.
