활성 5B로 SWE-Bench Pro 51%를 찍었다 — MAI-Code-1-Flash가 토큰을 깎은 방식

AI 딥다이브 2026년 06월 05일 (금) · 10:00 · 7분 읽기
목차
  • TL;DR
  • 배경 — 코드 모델 가성비 전쟁이 다시 점화됐다
  • 핵심 메커니즘 — Copilot 하니스 동형 학습 + 적응형 길이 제어
  • 코드 / 수식 — 적응형 길이 보상의 골격
  • 한계·반론
  • 현직 엔지니어 관점
  • 부록 — 더 읽을거리

TL;DR

  • 6/2 Microsoft Build 2026에서 공개된 MAI-Code-1-Flash는 137B 총 파라미터 중 5B만 활성화되는 MoE 코드 모델이고, SWE-Bench Pro에서 51.2%로 Claude Haiku 4.5(35.2%)를 16점 차로 앞섰다 (Microsoft AI — Introducing MAI-Code-1-Flash).
  • 핵심은 두 가지 — GitHub Copilot 하니스를 학습 루프에 그대로 끼워 넣은 "프로덕션 동형 학습"과, 문제 난이도에 따라 응답 토큰을 늘렸다 줄였다 하는 적응형 솔루션 길이 제어다. SWE-Bench Verified에서 동일 정답률에 토큰 60% 절감을 찍었다.
  • 한계도 또렷하다 — 적응형 길이는 결국 Copilot 환경 안에서만 검증됐고, 학습 데이터는 결국 Common Crawl 기반이며 (Simon Willison's Weblog — Microsoft's new MAI models), Einstellung 트랩 같은 적대적 카테고리는 여전히 50% 미만이다.

배경 — 코드 모델 가성비 전쟁이 다시 점화됐다

지난 두 달 코드 모델 시장은 가성비로 다시 갈렸다. 4월 Claude Haiku 4.5가 SWE-Bench Pro 35%대를 12B 클래스 가격에 풀었고, 5월 들어서는 Gemini 3 Flash와 GLM-Coder가 같은 가격대에 비집고 들어왔다. 그 위로는 Opus 4.8과 GPT-Codex-Pro가 60% 후반대를 차지하지만 토큰당 단가가 10배 차이다. "Haiku 가격에 Opus급 정확도"가 모두의 목표였다.

Microsoft가 6/2 Build에서 던진 답은 MoE다. MAI-Code-1-Flash는 137B 전체 파라미터 중 5B만 토큰마다 활성화한다. 같은 날 공개된 MAI-Thinking-1(1T 전체·35B 활성)과 같은 가족이고, OpenAI에 의존하지 않고 자체 학습한 첫 코드 모델이라는 점에서 Microsoft 내부 로드맵의 상징적 분기점이다 (Microsoft AI — Hill-climbing machine: 7 new MAI models).

핵심 메커니즘 — Copilot 하니스 동형 학습 + 적응형 길이 제어

[사용자 요청]
    │
    ▼
[난이도 분류기] ──→ 간단: 짧은 응답 예산
    │              복잡: 깊은 추론 예산
    ▼
[MoE 라우터 (전문가 N개 중 k=2 활성)]
    │
    ▼
[5B 활성 경로 · 137B 전체 풀] ── 학습 시 GitHub Copilot 하니스에서 직접 평가
    │
    ▼
[툴 호출(파일 수정·테스트 실행) 또는 최종 답]

학습 단계에서 체크포인트마다 GitHub Copilot이 프로덕션에서 쓰는 하니스 — 파일 트리 탐색, 테스트 실행, 패치 적용 — 를 그대로 띄워 평가한다. 일반 SWE-Bench 점수만 보지 않고 텔레메트리 기반 실제 워크플로 통과율을 함께 추적한다는 게 차별점이다. "오프라인 개선이 프로덕션 품질로 옮겨가는 신호"를 학습 루프 안에서 직접 본다.

적응형 솔루션 길이 제어는 강화학습 보상에 토큰 수가 들어간다. 같은 정답을 더 짧게 내면 보상이 크고, 어려운 문제일수록 토큰 예산을 늘려야 통과 확률이 오른다. 모델은 자기가 처한 난이도에 맞춰 응답 길이를 스스로 조절하도록 학습된다.

코드 / 수식 — 적응형 길이 보상의 골격

# 의사코드: adaptive solution length 보상 (실제 학습 코드 아님)
def reward(rollout, ground_truth):
    passed = run_in_copilot_harness(rollout, ground_truth)
    tokens = len(rollout.solution_tokens)
    if not passed:
        return -1.0
    # 통과했을 때만 토큰 패널티 부과 — 짧을수록 가산점
    # alpha는 난이도에 반비례하게 스케줄링
    alpha = schedule_by_difficulty(ground_truth.difficulty)
    return 1.0 - alpha * (tokens / TOKEN_BUDGET)

핵심은 통과 여부 보상에 토큰 패널티를 곱이 아닌 합으로 얹는 것 — 곱으로 묶으면 어려운 문제에서 모델이 아예 짧게 포기하는 쪽으로 무너진다. 합 구조에서 난이도별 alpha를 다르게 잡아주면, 쉬운 문제는 절약, 어려운 문제는 충분한 추론이라는 분기 행동이 자연스럽게 나온다. SWE-Bench Verified에서 토큰 60% 절감이 가능했던 이유다.

한계·반론

첫째, 벤치마크 비교 대상이 사실상 Haiku 4.5 하나다. 같은 발표 자료에서 Gemini 3 Flash·GLM-Coder·DeepSeek-Coder-V3 같은 동급 경쟁자와의 표는 빠져 있다. Microsoft 입장에서 가장 직접적인 경쟁자가 Anthropic이라 비교 대상을 좁힌 건 이해되지만, 가성비 주장의 검증은 외부 ELO 보드에서 한 번 더 봐야 한다.

둘째, "프로덕션 동형 학습"은 양날의 검이다. Copilot 하니스 안에서는 강하지만, Cursor·Continue·자체 IDE 통합 등 다른 하니스에서는 같은 점수를 기대하기 어렵다. 모델이 학습한 툴 호출 시퀀스가 Copilot 쪽 컨벤션에 묶여 있기 때문이다.

셋째, 학습 데이터 라이선스 문제는 결국 같다. 발표문은 "clean and appropriately licensed"라고 썼지만, MAI-Thinking-1 기술 보고서를 보면 자체 크롤 1.2T 페이지를 794B로 필터링하고 Common Crawl을 24.2B 페이지 추가했다 (Simon Willison's Weblog — Microsoft's new MAI models). 다른 대형 모델과 본질적으로 같은 출처고, 코드 모델 한정 라이선스 청정성은 아직 시장에 없다.

넷째, Microsoft 자체 적대적 벤치마크(186문항·34카테고리)에서 Einstellung 트랩 카테고리는 50% 미만이다. 익숙한 패턴에 매몰되면 정답을 놓친다는 뜻이고, 코드 리팩토링 같은 "기존 코드를 의심하고 뜯어내는" 작업에서 약점이 될 수 있다.

현직 엔지니어 관점

활성 5B는 온디바이스 추론의 현실적 문턱이다. 양자화하면 RTX 4090 한 장에 활성 경로가 들어가고, M3 Max 64GB에서도 충분히 돈다. 전체 137B를 메모리에 올려 두는 부담은 남지만, 라우터가 활성 전문가만 골라서 계산하므로 추론 FLOPS는 작은 모델 수준이다. 데이터센터 측면에서 보면 같은 H100 시간에 처리할 수 있는 토큰 수가 Dense 모델의 3~5배가 되고, 이게 본질적으로 "Haiku 가격에 Pro급 정확도"라는 회사 외부 메시지의 하드웨어 근거다. 반도체 입장에서 흥미로운 건 활성 5B라는 숫자가 곧 차세대 NPU의 일관성 있는 설계 타깃이 된다는 점 — Snapdragon X2 Elite, M4 Pro, Tensor G6 같은 SoC가 8~16B 활성 MoE를 1차 표적으로 잡기 시작하면, 온디바이스 코드 어시스트가 클라우드 호출 없이 1년 안에 자리잡을 수 있다.
