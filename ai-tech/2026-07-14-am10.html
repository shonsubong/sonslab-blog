테스트가 못 잡는 버그를 증명이 잡는다 — Leanstral 1.5

AI 딥다이브 2026년 07월 14일 (화) · 10:00 · 5분 읽기

TL;DR

  • Mistral이 6월 30일 Lean 4 증명 전용 에이전트 모델 Leanstral 1.5를 Apache 2.0으로 공개했다. 119B MoE, 활성 6.5B (Mistral — Leanstral 1.5)
  • miniF2F 100% 포화, PutnamBench 672문제 중 587개 해결. 문제당 약 4달러로, 300달러대 경쟁 모델 대비 비용이 두 자릿수 낮다
  • 수학용으로 훈련했는데 실제 오픈소스 저장소 57곳에서 버그 11개를 찾아냈다. 그중 5개는 GitHub에 보고된 적 없던 것

배경 — 왜 지금인가

요즘 새 코드의 상당량을 AI가 쓴다. 문제는 그 코드의 테스트도 AI가 쓴다는 점이다. 같은 모델이 코드와 테스트를 쓰면 사각지대도 같이 공유한다. 테스트가 전부 통과해도 안심할 근거가 예전만 못하다는 이야기다.

형식 검증은 이 구도에서 자유로운 유일한 품질 기준이다. "아마 맞을 것"이 아니라 코드의 성질을 수학적으로 증명하기 때문에, 누가 코드를 썼는지를 따지지 않는다. 지금까지는 사람 손이 너무 많이 들어 항공·의료 같은 분야만 감당할 수 있었는데, Mistral이 6월 30일 공개한 Leanstral 1.5는 이 증명 작업 자체를 에이전트에게 맡긴다 (Mistral — Leanstral 1.5). 이달 들어 자율 랜섬웨어 사례가 보고되고 Anthropic이 취약점 자동 수리 프로그램을 3배로 늘리는 등, 코드 신뢰성 문제가 보안 이슈로 번지는 시점이라 타이밍이 절묘하다.

핵심 메커니즘

Leanstral 1.5는 증명 지원 도구 Lean 4 (leanprover/lean4) 위에서 도는 코드 에이전트다. 한 번에 증명을 뽑아내는 게 아니라, 컴파일러와 왕복하며 고쳐 나간다.

[정리·속성 제시] → [Leanstral: 증명 작성] → [Lean 4 컴파일러 검사]
        ↑                                          │
        └── 목표(goal)·오류·타입 정보 (LSP 피드백) ─┘
             실패 시 보조 정리 추가·전략 수정 후 재시도

구조는 128개 전문가 중 4개가 활성화되는 MoE로, 전체 119B에 토큰당 6.5B만 계산한다. 훈련은 중간 훈련, 지도 미세조정, CISPO 강화학습 3단계인데, 강화학습 환경이 둘이라는 점이 특징이다. 하나는 정리를 받아 증명·반증을 반복하는 다중 턴 환경, 다른 하나는 파일 시스템에서 파일을 고치고 bash를 실행하며 Lean 언어 서버를 조회하는 코드 에이전트 환경이다. 덕분에 저장소 안의 미완성 증명을 이어받거나, 문맥 압축을 거치며 수백만 토큰짜리 작업을 지속할 수 있다.

성능은 시험 시간 연산에 비례해 늘어난다. PutnamBench 기준 시도당 5만 토큰이면 44문제, 100만 토큰이면 493문제, 400만 토큰이면 587문제까지 올라간다. 증명이라는 과제가 검증 가능한 보상이라 시험 시간 스케일링과 궁합이 좋다는 걸 보여주는 곡선이다.

코드 예시 — 실제로 잡힌 버그

Rust 코드를 Aeneas로 Lean에 번역한 뒤, Leanstral이 사용자 의도를 추론해 정확성 속성을 만들고 증명과 반증을 각각 시도하는 파이프라인이 공개됐다 (Mert Ünsal(@mertunsal2020) X thread). datrs/varinteger의 zigzag 복호 부호 함수에서 잡힌 버그가 대표 사례다.

// varinteger의 부호 계산 (요지)
fn sign(value: u64) -> i64 {
    // value == u64::MAX 이면 value + 1 이 오버플로한다
    // 디버그 빌드: 패닉 / 릴리스 빌드: 조용한 값 손상
    let half = (value + 1) / 2;
    ...
}

-- Leanstral이 만든 속성의 골격: 모든 입력에서 복호가 명세와 일치하는가
theorem sign_correct (v : U64) : decode_sign v = spec_sign v := by
  ...  -- v = U64.MAX 에서 반증됨 → 버그 확정

증명이 실패하고 반증이 성공하면 그게 곧 버그 리포트다. 테스트 케이스를 사람이 떠올릴 필요가 없다는 점이 기존 퍼징·단위 테스트와 다르다.

한계와 반론

증명은 명세만큼만 유효하다. Leanstral이 추론한 속성이 사용자 의도와 어긋나면, 엉뚱한 것을 완벽하게 증명하는 상황이 된다. 57개 저장소에서 위반 속성 47개 중 진짜 버그는 11개였다는 숫자가 이 간극을 보여준다. Aeneas가 번역할 수 있는 Rust 부분집합도 제한적이라 아직 모든 코드베이스에 적용할 수 있는 건 아니다.

비용도 만만치 않다. 문제당 4달러는 경쟁 대비 저렴한 것이지 절대적으로 싼 게 아니고, AVL 트리의 시간 복잡도 증명 하나에 270만 토큰과 22회의 문맥 압축이 들었다. miniF2F 100%는 벤치마크 포화 신호라 다음 세대 평가 기준이 필요하다는 뜻이기도 하다. 9월 30일 API 종료가 예고된 실험적 배포라는 점도 확인이 필요한 부분이다.

현직 엔지니어의 한 문단

장비 제어 소프트웨어나 펌웨어처럼 실패 비용이 큰 코드는 테스트 커버리지 숫자보다 "이 조건에서 절대 오버플로하지 않는다"는 보장이 필요하다. 위 varinteger 사례가 정확히 그 부류다. 활성 6.5B라 추론 비용이 낮은 것도 좋지만, 온디바이스용이라기보다는 CI에 증명 단계를 하나 끼워 넣는 그림에 가깝다. 개인적으로 주목하는 변화는 역할 이동이다. 코드는 AI가 쓰고 증명도 AI가 쓴다면, 엔지니어의 일은 "무엇을 보장해야 하는가"를 명세로 적는 쪽으로 옮겨간다. 명세를 쓰는 능력이 코드를 쓰는 능력보다 귀해지는 시점이 생각보다 빨리 올 수 있다.
