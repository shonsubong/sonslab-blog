지우는 것도 능력이다 — 1M 컨텍스트를 스스로 관리하는 Muse Spark 1.1

AI 딥다이브 2026년 07월 15일 (수) · 10:00 · 6분 읽기

TL;DR

  • Meta가 7월 9일 Muse Spark 1.1을 내놓으면서 첫 유료 개발자 API인 Meta Model API 공개 프리뷰를 열었다.
  • 헤드라인은 1M 토큰 컨텍스트지만, 진짜 볼거리는 모델이 스스로 요약·압축·검색을 결정하는 "능동 컨텍스트 관리"다.
  • 긴 에이전트 작업에서 무엇을 남기고 무엇을 지울지 모델이 판단한다. 컨텍스트 창은 이제 저장 공간이 아니라 관리 대상이다.

배경 (Why now)

지난주는 모델 발표가 몰린 주였다. 7월 8일 Grok 4.5, 9일 GPT-5.6, 그리고 같은 날 Meta Superintelligence Labs가 Muse Spark 1.1을 공개했다 (Meta AI — Introducing Muse Spark 1.1). Llama를 무료로 뿌리던 Meta가 처음으로 돈을 받고 모델을 파는 API를 열었다는 점에서 사업적으로도 전환점이다. 입력 100만 토큰당 $1.25, 출력 $4.25로 가격은 공격적이다 (TechCrunch — Meta enters the crowded AI coding battle).

발표문에서 내 눈길을 끈 건 벤치마크 표가 아니라 한 문장이었다. "Muse Spark 1.1은 1M 토큰 컨텍스트 창을 능동적으로 관리한다. 과거 행동을 기억하고, 훨씬 이전 작업에서 정보를 검색하며, 이후 작업에 필요한 핵심 단계를 보존하는 방식으로 압축한다." 직전 버전의 262K에서 1M으로 창이 넓어진 것보다, 그 창을 모델이 직접 정리한다는 쪽이 기술적으로 훨씬 흥미롭다 (ppc.land — Muse Spark 1.1 gains 1 million token context).

핵심 메커니즘

기존 긴 컨텍스트는 수동적이다. 창이 가득 차면 하네스(Claude Code 같은 도구)가 밖에서 요약을 만들어 대화를 이어 붙인다. 컴팩션 시점도, 요약 품질도 모델 바깥의 코드가 결정한다. Muse Spark 1.1은 이 관리 책임을 모델 안으로 들여왔다. 훈련 단계에서부터 계획 모드, 서브에이전트 위임, 컨텍스트 컴팩션 같은 하네스 기능을 다루도록 학습시켰다는 게 Meta의 설명이다.

동작 구조를 그려 보면 이렇다.

[관찰 축적] → [임계 감지] → [컴팩션: 핵심 단계 보존 + 나머지 요약]
     ↑                                        │
     └────── [아카이브 검색·복원] ←────────────┘

핵심은 컴팩션이 균일한 요약이 아니라는 점이다. 파일 경로, 실패 원인, 이미 내린 결정처럼 이후 단계가 의존하는 상태는 원문 그대로 남기고, 중간 관찰 로그만 요약으로 접는다. 그리고 필요해지면 접어 둔 초기 작업 내용을 다시 검색해서 꺼내 온다. 기억·검색·압축이 하나의 정책으로 묶인 셈이다.

코드 예시

발표문 설명을 에이전트 루프 의사코드로 옮기면 뼈대는 이 정도다.

# 능동 컨텍스트 관리의 뼈대 (의사코드)
def agent_loop(task, ctx):
    while not task.done():
        obs = execute(task.next_action(ctx))
        ctx.append(obs)

        if ctx.tokens() > SOFT_LIMIT:            # 임계 감지
            keep = ctx.select_critical()          # 파일 경로·실패 원인·결정 사항
            summary = model.summarize(ctx.stale()) # 오래된 관찰은 요약으로
            ctx.archive(ctx.stale())               # 원문은 아카이브로 이동
            ctx = Context(keep + [summary] + ctx.recent())

        if needs_recall(obs):                     # 초기 작업 재참조
            ctx.append(ctx.search_archive(obs.query))
    return task.result()

지금까지는 select_critical과 SOFT_LIMIT을 하네스 개발자가 손으로 짰다. Muse Spark 1.1은 이 판단 자체를 모델이 하도록 훈련했다는 주장이다.

한계·반론

컴팩션은 결국 손실 압축이다. 무엇이 "핵심 단계"인지는 모델 재량이고, 잘못 지우면 수백 스텝 뒤에서 조용히 무너진다. 실패가 컴팩션 시점이 아니라 한참 뒤에 드러나기 때문에 디버깅도 어렵다. 1M 능동 관리가 실제 장시간 작업에서 어느 정도 버티는지는 아직 3자 검증이 없다. 공개 프리뷰가 열린 지 일주일이 안 됐다.

Simon Willison은 4월 첫 Muse Spark 때 Meta 스스로 장기 에이전트·코딩 워크플로의 격차를 인정한 점이 벤치마크 서사를 약화시킨다고 짚었다 (@simonw — Introducing Muse Spark 1.1). 실제로 코딩 지표에서는 여전히 Anthropic과 OpenAI 최상위 모델에 못 미친다는 평가가 많다. "관리를 잘한다"와 "일을 잘한다"는 다른 문제다.

현직 엔지니어 관점

반도체 쪽에서 보면 이건 익숙한 그림이다. 1M 토큰 컨텍스트의 실체는 추론 서버 HBM을 점유하는 거대한 KV 캐시다. 창을 넓히는 경쟁은 결국 메모리 용량 경쟁인데, 능동 컴팩션은 방향이 다르다. 자주 쓰는 상태는 가까운 계층에 원문으로, 오래된 기록은 요약해서 먼 계층으로 보내는 메모리 계층화 발상을 모델 정책으로 구현한 것에 가깝다. 온디바이스에서는 이게 선택이 아니라 필수다. DRAM 몇 GB로 에이전트를 돌려야 하는 환경에서는 큰 창보다 잘 지우는 능력이 먼저다. 창 크기 경쟁의 다음 라운드는 "누가 더 크게"가 아니라 "누가 덜 잃고 줄이나"가 될 거라고 본다.
