대화에서 턴이 사라졌다 — GPT-Live 전이중 음성의 구조

AI 딥다이브 2026년 07월 11일 (토) · 10:00 · 7분 읽기
목차

  • 배경 (Why now)
  • 핵심 메커니즘
  • 코드 예시
  • 한계·반론

TL;DR

  • OpenAI가 7월 8일 GPT-Live를 공개했다. 듣기와 말하기를 동시에 하는 전이중(full-duplex) 음성 모델로, ChatGPT Voice의 기본 모델이 됐다.
  • 매 순간 "말할까, 들을까, 끼어들까, 도구를 부를까"를 초당 여러 번 판단한다. 검색·추론이 필요하면 GPT-5.5에 백그라운드로 위임하고, 그동안 대화는 끊기지 않는다.
  • 상호작용과 지능을 분리한 설계라 뒤의 프런티어 모델이 바뀌어도 음성 쪽은 그대로 간다. 음성 에이전트의 기본 구조가 이쪽으로 수렴할 가능성이 크다.

배경 (Why now)

이번 주 OpenAI는 발표를 몰아서 냈다. 7월 9일 GPT-5.6 Sol·Terra·Luna 공개에 하루 앞서, 7월 8일 음성 쪽에서 GPT-Live를 내놨다 (OpenAI — Introducing GPT-Live). 매주 1억 5천만 명이 쓰는 ChatGPT Voice의 기본 모델이 통째로 교체된 것이라, 모델 발표 러시 속에서도 체감 변화는 이쪽이 더 클 수 있다.

기존 Advanced Voice Mode는 턴 기반이었다. 침묵으로 턴의 끝을 감지하기 때문에, 생각하느라 잠깐 멈추면 모델이 끼어들고, 주변 소음에 턴이 끊겼다. 전이중 구조 자체는 새 개념이 아니다. Kyutai의 Moshi가 2024년에 오픈소스로 먼저 보여줬다 (Kyutai — Moshi 논문). 다만 프런티어급 제품의 기본값이 된 것은 이번이 처음이다.

핵심 메커니즘

세 세대를 나란히 놓으면 구조 차이가 보인다.

캐스케이드:  [음성] → STT → LLM → TTS → [음성]        (턴마다 3개 모델 릴레이)
턴 기반:    [음성] ─ 침묵 감지 → 단일 모델 → [음성]     (턴은 여전히 존재)
전이중:     사용자 스트림  ──●──●──●──●──●──→
                            ↕ 매 프레임 동시 처리
            모델 스트림    ──○──"mhmm"──○──○──→
                              └→ (위임) GPT-5.5 백그라운드 → 결과 복귀

전이중 모델은 대화를 메시지의 교환이 아니라 두 개의 연속 오디오 스트림으로 본다. 사용자 스트림과 모델 자신의 스트림을 같은 시간축 위에서 함께 모델링하고, 매 프레임 말하기·듣기·침묵·개입·도구 호출 중 하나를 고른다. 침묵도 예측 대상이라는 점이 핵심이다. "지금은 말하지 않는다"가 매 순간의 능동적 결정이 되면서, 맞장구("mhmm")와 기다림이 모두 계산의 결과가 된다.

OpenAI는 내부 구조를 공개하지 않았지만, 공개된 유사 시스템인 Moshi는 신경 코덱으로 오디오를 80ms 프레임 토큰으로 바꿔 두 스트림을 병렬 처리하고 이론 지연 160ms 수준을 달성했다. GPT-Live가 같은 계열의 구조라고 보는 게 합리적인 추정이다.

두 번째 축은 위임이다. 검색이나 깊은 추론이 필요하면 GPT-Live는 그 작업을 GPT-5.5에 넘기고 자기는 대화를 계속한다. 접수 담당자가 손님과 이야기를 이어가는 동안 뒤에서 전문가가 일하는 그림이다. GPQA·BrowseComp 점수가 Advanced Voice Mode 대비 크게 오른 것도 이 위임 덕분이다 (OpenAI 발표의 평가 절).

코드 예시

Moshi 계열 구조를 기준으로 한 전이중 프레임 루프 의사코드다.

# 전이중 음성 모델의 프레임 루프 (의사코드)
codec = NeuralCodec(frame_ms=80)             # 80ms마다 오디오 토큰 1프레임
state = model.init_state()

while call.active:
    user_tok = codec.encode(mic.read(80))    # 듣기: 사용자 스트림
    out = model.step(state, user_tok)        # 두 스트림을 한 시간축에서 처리
    if out.action == "SPEAK":
        speaker.play(codec.decode(out.tok))  # 말하기 (사용자 발화와 겹쳐도 됨)
    elif out.action == "BACKCHANNEL":
        speaker.play(codec.decode(out.tok))  # "mhmm" 짧은 맞장구
    elif out.action == "DELEGATE":
        job = spawn(gpt55.run, out.task)     # 백그라운드 위임, 대화는 계속
    # "SILENCE"면 재생 없이 다음 프레임 — 기다림도 예측의 결과
    if job and job.done():
        state = model.inject(state, job.result)  # 결과를 대화에 복귀

턴 기반 모델에는 이 루프 자체가 없다. 침묵 감지기가 턴을 잘라준 뒤에야 모델이 돌기 시작한다.

한계·반론

먼저 이 글의 메커니즘 설명은 유추라는 점을 분명히 해둔다. OpenAI는 아키텍처 세부를 공개하지 않았고, 시스템 카드도 안전성 중심이다 (GPT-Live System Card).

전이중의 그늘은 "끼어들 자유"가 "잘못 끼어들 자유"이기도 하다는 점이다. 몇 주 먼저 써본 Simon Willison은 말하는 도중 모델이 농담도 아닌 말에 웃으며 끼어드는 버그를 겪었다고 적었다 (Simon Willison — Introducing GPT-Live). 턴 기반에서는 구조적으로 불가능했던 종류의 오류다.

언어 문제도 남아 있다. 인기 언어 위주로 최적화됐고 일부 언어는 억양이나 유창성에 공백이 있다고 OpenAI 스스로 밝혔다. 한국어 품질은 직접 확인이 필요하다. 출시 시점에는 영상·화면 공유도 지원하지 않는다.

벤치마크 해석에도 함정이 있다. GPQA·BrowseComp 향상은 위임받는 GPT-5.5의 능력이지 음성 모델 자체의 지능이 아니다. 인간 선호 평가에서 75.7%가 GPT-Live를 골랐다는 수치도 대화의 자연스러움을 잰 것이지 정답률이 아니다 (MarkTechPost — GPT-Live 분석). 그리고 대화가 자연스러워질수록 감정 의존은 커진다. OpenAI가 시스템 카드에서 emotional reliance 모니터링을 별도 항목으로 둔 이유다.

현직 엔지니어 관점

위임 구조가 온디바이스와 잘 맞는다는 게 눈에 들어온다. 상호작용을 맡는 쪽은 작고 빨라야 하고, 지능을 맡는 쪽은 크고 느려도 된다. 이 분업은 그대로 "NPU 위의 소형 전이중 모델 + 클라우드 프런티어 모델"로 옮겨진다. mini 버전을 무료 사용자 기본값으로 같이 낸 것도 소형화가 이미 상당히 진행됐다는 신호로 읽힌다. 다만 80ms 프레임마다 인코딩과 판단을 끝내려면 엣지의 지연 예산이 빠듯하고, 스피커 출력이 마이크로 되돌아오는 상황에서 두 스트림을 깨끗이 분리하려면 에코 제거 같은 오디오 프런트엔드가 다시 중요해진다. 모델이 좋아질수록 마이크 앞단의 신호 처리가 병목이 되는, 하드웨어 하는 사람 입장에선 익숙한 순서다.
