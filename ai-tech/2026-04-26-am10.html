DeepSeek V4의 MoE 라우팅이 H100을 두 배로 늘려놓는 법

TL;DR

  • DeepSeek V4(4/24 공개)는 671B 파라미터를 가졌지만 토큰당 활성 파라미터는 37B에 불과한 MoE 구조다.
  • 핵심은 "expert routing" — 같은 GPU 클러스터로 dense 모델 대비 거의 두 배의 유효 처리량을 뽑아낸다.
  • 온디바이스에는 직접 못 가지만, 라우팅 아이디어 자체는 엣지 추론 최적화에 그대로 옮길 수 있다.

배경 — 왜 지금 MoE인가

지난 며칠 동안 데일리에서 DeepSeek V4 공개와 GPT-5.5 가격 인하를 따로 다뤘다. 두 사건은 사실 한 흐름이다. 모델 학습 비용이 한 자릿수 백만 달러까지 내려오는 동안, 추론 비용이 그만큼 빠르게 떨어지지 않으면 의미가 없다. MoE(Mixture of Experts)는 추론 비용을 학습과 분리해서 떨어뜨리는 가장 현실적인 길이다.

dense 모델은 모든 토큰이 모든 파라미터를 통과한다. 671B 모델이라면 토큰 한 개당 671B만큼의 행렬 곱이 필요하다. MoE는 다르다. 라우터(작은 신경망)가 각 토큰마다 어느 expert를 쓸지 결정하고, 선택된 expert만 활성화된다. DeepSeek V4의 경우 256개 expert 중 8개만 토큰당 활성 — 그래서 유효 파라미터가 37B로 떨어진다.

핵심 메커니즘 — 토큰 라우팅

[입력 토큰] ──> [Router (linear + softmax)] ──> top-k expert 선택
                          │
                          ▼
        ┌──────────┬──────────┬──────────┬──────────┐
        │ Expert 1 │ Expert 2 │   ...    │ Expert N │
        └──────────┴──────────┴──────────┴──────────┘
                          │
                          ▼  (활성된 expert 출력의 가중합)
                       [출력]

라우터는 토큰 임베딩을 받아 expert별 점수를 매기고, 상위 k개(보통 1~2개)를 선택한다. 어려운 점은 두 가지다.

  1. 로드 밸런싱 — 라우터가 한쪽 expert로만 토큰을 몰면 GPU 활용률이 망가진다. DeepSeek V4는 auxiliary loss + sequence-level balance 손실을 함께 써서 expert별 활성 빈도를 평탄화한다.
  2. 통신 비용 — expert가 여러 GPU에 흩어져 있으면 토큰을 해당 GPU로 보내고(all-to-all) 결과를 다시 받아오는 통신이 dense 대비 두세 배 든다. DeepSeek는 이 부분을 node 내부 라우팅을 우선시(device-limited routing)해서 inter-node 통신을 절반 가까이 줄였다고 보고한다.

코드로 보는 라우팅 — 30줄 의사코드

실제 DeepSeek 구현은 PyTorch 기반이고 통신 최적화가 핵심이지만, 라우팅 자체의 본질은 단순하다.

import torch
import torch.nn as nn
import torch.nn.functional as F

class TopKRouter(nn.Module):
    def __init__(self, hidden_dim, num_experts, top_k=2):
        super().__init__()
        self.gate = nn.Linear(hidden_dim, num_experts, bias=False)
        self.top_k = top_k

    def forward(self, x):  # x: [batch, seq, hidden]
        logits = self.gate(x)                       # [B, S, E]
        scores = F.softmax(logits, dim=-1)
        top_w, top_idx = scores.topk(self.top_k, dim=-1)  # [B, S, k]
        # 정규화: 선택된 k개만 가중치 합이 1이 되도록
        top_w = top_w / top_w.sum(dim=-1, keepdim=True)
        return top_w, top_idx

# 추론 단계: 토큰별로 선택된 expert만 forward
def moe_forward(x, router, experts):
    weights, indices = router(x)
    out = torch.zeros_like(x)
    for k in range(weights.size(-1)):
        for e in range(len(experts)):
            mask = (indices[..., k] == e)
            if mask.any():
                out[mask] += experts[e](x[mask]) * weights[..., k][mask].unsqueeze(-1)
    return out

실전 구현은 이 이중 루프를 GPU 친화적으로 풀어야 한다 — dispatch / combine 커뮤니케이션 커널이 핵심이고, DeepSeek-MoE 논문과 Megablocks가 좋은 참고다.

한계와 반론

  • 메모리는 줄지 않는다. expert가 모두 GPU에 올라가 있어야 하므로 671B 모델은 여전히 671B만큼의 VRAM을 잡아먹는다. 추론 연산은 줄지만 메모리는 그대로다.
  • 라우팅 불안정성. 작은 모델에서는 expert 활용 편중이 심하다. DeepSeek가 잘 되는 이유 중 하나는 모델이 충분히 크기 때문이다 (Switch Transformer 분석에서 비슷한 관찰).
  • 벤치마크 함정. "활성 파라미터 37B = dense 37B와 동급"은 거짓에 가깝다. expert 다양성 덕분에 표현력은 더 크지만, 짧은 컨텍스트·간단한 태스크에서는 dense 7B보다 못한 경우도 보고된다 (Sebastian Raschka의 분석).

현직 엔지니어 관점

반도체 현장에서 MoE 라우팅 아이디어는 온디바이스 추론 최적화로 그대로 옮길 수 있다. 모바일 NPU에 dense 7B 모델을 통째로 올리는 건 메모리·전력 모두 부담이지만, "라우터가 5개 task-specific subnetwork 중 하나를 고르고 그것만 메모리로 swap-in"하는 구조는 충분히 가능하다. Apple이 iOS 자체 모델에 비슷한 패턴을 쓴다는 관찰이 @karpathy의 X 노트에서도 언급된 적이 있다. DeepSeek가 보여주는 건 결국 "조건부 계산이 통한다"는 점이고, 이게 통하면 엣지에서 모델 크기를 늘릴 여지가 한 단계 더 생긴다. 개인 PC에서 Claude Code 쓰면서 항상 답답한 토큰 throughput이, 이런 라우팅이 클라이언트단까지 내려오는 날에는 좀 풀릴 것 같다.
