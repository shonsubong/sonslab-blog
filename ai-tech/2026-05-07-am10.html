투기 디코드가 4배 가속에 도달한 길 — EAGLE-3와 자기 드래프트의 합류

AI 딥다이브 2026년 05월 07일 (목) · 10:00 · 5분 읽기
목차

TL;DR

  • 투기 디코드(speculative decoding)는 작은 드래프트로 K개 토큰을 먼저 뽑고, 큰 타깃 모델이 한 번의 forward에 모두 검수해 디코드 처리량을 늘리는 기법이다.
  • 1세대 SpecDec(별도 드래프트 모델)이 K=4에서 1.5~2배에 머물던 것이, EAGLE-3와 자기 드래프트(self-draft) 계열에서 4~5배까지 늘었다.
  • 핵심 변화는 acceptance rate. 드래프트 단계에서 타깃 모델의 hidden state를 직접 받는 구조로 80%대까지 끌어올렸다.

배경 (Why now)

원조 SpecDec(Leviathan 등, arXiv:2211.17192)은 별도 작은 모델을 드래프트로 두는 방식이라, 두 모델 분포 차이 때문에 acceptance가 50% 부근에서 정체됐다. 직전 1~2주에 흐름이 다시 굳어졌다. vLLM v0.11이 EAGLE-3 백엔드를 default로 승격했고 (vLLM SpecDec 문서), DeepSeek V3.1이 Multi-Token Prediction(MTP) 헤드를 모델 자체에 통합해 공개했다 (DeepSeek-V3 Technical Report). Together AI가 4월 말 Llama 3.3 70B에 EAGLE-3을 붙여 4.2배 가속을 보고했고 (Together — EAGLE-3 통합), 이로써 "별도 모델 두 개" 시대가 끝났다는 인식이 자리 잡았다.

핵심 메커니즘

[원조 SpecDec]
입력 → [작은 드래프트 모델] → K개 토큰 체인
                                    ↓
                  [타깃 모델] 1회 forward, 모든 위치 동시 검증
                                    ↓
              acceptance 통과한 0~K개만 채택, 나머지 폐기

[EAGLE-3 / MTP]
입력 → [타깃 모델 forward 1회] → hidden state h_t
                                    ↓
          [경량 드래프트 헤드] ← h_t 직접 입력
                                    ↓
          K개 후보 트리 → 같은 forward에서 검증

핵심 차이 두 가지. 첫째, 드래프트가 별도 모델이 아니라 타깃 모델의 잠재 표상에 붙는 작은 헤드(layer 1~2개)다. 둘째, 후보를 선형 체인이 아닌 트리로 펼쳐, 한 번의 검증에서 더 많은 가지를 평가한다 (EAGLE-3 — arXiv:2503.01840). 분포 일치도가 올라가니 acceptance가 60~80%로 뛰고, 드래프트 비용은 메인 forward 대비 5% 미만으로 떨어진다.

코드 / 수식 예시

투기 디코드의 정수는 rejection sampling이다. 드래프트 분포 $q$, 타깃 $p$일 때 한 토큰의 채택 확률은

$$ a = \min!\left(1,\, \frac{p(x)}{q(x)}\right) $$

이고, 거부되면 보정 분포 $\max(0,\, p-q)$에서 다시 샘플링한다. 출력 분포가 정확히 $p$와 같음이 보장된다.

def speculative_step(draft_logits, target_logits, draft_token):
    p = F.softmax(target_logits, dim=-1)[draft_token]
    q = F.softmax(draft_logits,  dim=-1)[draft_token]
    if torch.rand(()) < min(1.0, (p / q).item()):
        return draft_token, True            # 채택
    # 거부 → 보정 분포에서 재샘플
    resid = (F.softmax(target_logits, -1)
             - F.softmax(draft_logits, -1)).clamp(min=0)
    resid = resid / resid.sum()
    return torch.multinomial(resid, 1).item(), False

EAGLE-3은 위 식 자체는 그대로 두고, $q$를 만드는 드래프트 헤드 구조만 바꾼다. 출력이 타깃과 동일하다는 보장이 깨지지 않는다는 게 이 계열의 매력이다.

한계·반론

첫째, acceptance rate는 도메인에 민감하다. 코드 보조처럼 토큰 분포가 좁은 작업은 70%를 넘지만, 자유 작문이나 다국어 코드 스위칭은 50%대로 내려앉는다는 보고가 있다 (SemiAnalysis).

둘째, 트리 디코드는 길이가 깊어질수록 GPU 캐시 라인을 깨뜨려 이득이 사라진다. EAGLE-3 논문도 트리 깊이 5 이상에서 한계 효율이 급락한다고 인정한다.

셋째, 배치가 큰 서빙(연속 배치 32+)에서는 디코드 자체가 이미 컴퓨트 한계에 가까워, SpecDec이 노릴 슬랙이 줄어든다. 즉 "작은 배치·낮은 latency" 워크로드에서만 4배 이득이 실제로 나온다.

현직 엔지니어 관점

온디바이스 NPU 관점에서 SpecDec은 이론적으로 가장 매력적인 가속 기법이다. 모바일·자동차 SoC는 디코드 단계가 100% 메모리 대역폭에 묶여 있고, K개 토큰을 한 forward로 묶으면 가중치 페치 비용이 1/K로 떨어지기 때문이다. 다만 실전 도입은 두 가지 벽에 막혀 있다. 첫째, NPU 컴파일러는 동적 트리 구조를 잘 다루지 못한다 — 정적 그래프 가정이 깊게 자리 잡고 있어, 런타임에 acceptance 여부에 따라 길이가 달라지는 디코드 트리는 풀어내기 까다롭다. 둘째, 타깃 모델 hidden state를 매 토큰마다 드래프트 헤드로 보내는 데이터 흐름은 NPU 내부 스크래치패드에 추가 압력을 준다. 결과적으로 클라우드 GPU에서 4배가 모바일 NPU에서 1.5배로 깎이는 그림이 흔하다. 그래도 K=2의 가벼운 자기 드래프트만 붙여도 LPDDR 대역폭 절반을 깎을 수 있어, 다음 1년 안에 칩셋 SDK가 SpecDec 트리 디코드를 1차 객체로 받을 가능성이 높다.
